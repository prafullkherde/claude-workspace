Foundation

JVM — How Java Actually Runs

The JVM is Java's V8 engine + Node.js runtime combined. Before Spring Boot makes sense, this must be clear.

🧠 Mental Model

In JavaScript: you write .js → V8 reads it → executes directly. In Java: you write .java → compiler turns it into .class (bytecode) → JVM runs the bytecode. The bytecode is platform-neutral — it runs on any JVM, on any OS. That's the "Write Once, Run Anywhere" promise.

JDK vs JRE vs JVM — The Three Layers

JDK — Java Development Kit
javac compiler + JRE + debugging tools. You install this on dev machines.

Bundled in JDK
JVM — Java Virtual Machine
Executes bytecode. Manages memory (GC), threads, JIT compilation, security sandbox.

JVM Memory — Heap vs Stack
// Stack: method calls, local variables
// Each thread gets its own stack
public void processOrder(Order order) {
    int total = order.getTotal(); // stack
    // ^^ lives here only during method
}

// Heap: all objects live here
// Shared across threads
// Managed by Garbage Collector
Order order = new Order(); // heap
List<Item> items = new ArrayList<>(); // heap

// GC automatically frees unreachable objects
// No manual free() like C/C++
// But can cause GC pause → latency spikes
JIT Compilation — Why Java Gets Faster Over Time
// JIT = Just-In-Time compilation
// JVM starts interpreting bytecode (slow)
// Tracks "hot" code paths
// Compiles hot paths to native machine code

// Example: this loop runs 1M times
for (int i = 0; i < 1000000; i++) {
    doWork();  // JIT makes this native after ~10k
}

// ⚡ That's why Java apps are slow to start
// but reach near-C++ speed after warmup
// GraalVM Native Image solves cold start
// → compiles to native binary ahead of time

☕
JVM Hook

JVM = a fake computer inside your real computer. Java programs run on this fake computer. The JVM translates "fake computer instructions" (bytecode) to real CPU instructions. That's why Java runs everywhere — every OS has its own JVM translator.

🧹
Garbage Collector Hook

GC = hotel housekeeping. Objects are guests. When a guest checks out (no more references), housekeeping cleans up automatically. You never call "free memory" — GC does it. But housekeeping takes time → that's the "GC pause" problem.

🔥
JIT Hook

JIT = a chef who gets faster as orders repeat. First pancake = slow (read recipe carefully). After 1000 pancakes = muscle memory, full speed. JVM "learns" your code's hot paths and compiles them to native speed. That's why Java warms up slowly but runs fast.

⚡ Recall Trigger
JDK = install on dev machine (includes compiler). JVM = the engine that runs bytecode. Bytecode = platform-neutral instructions (.class files). Heap = all objects live here, GC manages it. Stack = method calls + locals, per-thread. JIT = hot code paths become native machine code over time. Java 21 LTS = use this for Spring Boot 3.

groupId:artifactId:version — The Java Package Address
// npm: "express": "^4.18.0"
// Maven uses THREE parts: groupId + artifactId + version

// groupId    = company/org namespace (like npm scope @company/)
// artifactId = the specific library name
// version    = exact or range

<dependency>
  <groupId>org.springframework.boot</groupId>   <!-- org -->
  <artifactId>spring-boot-starter-web</artifactId><!-- library -->
  <!-- version managed by Spring Boot BOM -->

// That's the ~/.m2 folder = Java's node_modules (but GLOBAL, shared)
// Once downloaded, never downloaded again for any project

Spring Boot Parent POM — The BOM (Bill of Materials)

Parent POM = Shared Version Management
<!-- This single line manages 300+ dependency versions -->
<parent>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-parent</artifactId>
  <version>3.2.0</version>
</parent>

<!-- Now you DON'T need to specify versions for Spring deps -->
<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-data-jpa</artifactId>
  <!-- No version needed! Parent manages it -->
</dependency>

<!-- Same for Hibernate, Jackson, Tomcat, etc -->
<!-- Spring Boot guarantees ALL these versions work together -->
<!-- That's the "opinionated defaults" Spring Boot is famous for -->
🏦
~/.m2 Hook

~/.m2 = global bank vault for Java jars. npm downloads to node_modules per project (10 projects = 10 copies). Maven downloads to ~/.m2 ONCE (10 projects = 1 copy + 10 symlinks). CI machines start fresh → must download again. Use a Nexus proxy to cache.

🧾
BOM / Parent POM Hook

Parent POM = restaurant set menu. You say "I want the Spring Boot set." Chef (Maven) picks all compatible dishes (library versions). You don't pick each dish separately. Override one item if needed — but Spring guarantees the set works together.

📦
Fat JAR Hook

Maven packages → .jar (fat jar). This jar contains YOUR code + ALL dependencies inside one file. Like a self-contained shipping container. java -jar myapp.jar = instant run, no npm install needed. That's why Spring Boot deployments are so easy.

🔄 What Breaks Without Understanding Maven
  • Version conflicts → Two libraries need different versions of the same transitive dep. Maven picks one silently — wrong one can cause runtime exceptions.
  • Not using parent POM → Specifying versions manually → incompatible library combinations → cryptic ClassNotFoundException at runtime.
  • Missing scope=test → Test libraries bundled into production jar → larger artifact, possible security issues.
  • Skipping mvn clean → Stale .class files from deleted source → mysterious runtime behavior that doesn't match code.
  • Not checking ~/.m2 on CI → Every build downloads all dependencies → 5-minute CI builds, rate-limited by Maven Central.
⚡ Recall Trigger
pom.xml = package.json for Java. ~/.m2 = global npm cache (shared across projects). groupId:artifactId:version = 3-part address for any Java library. Parent POM / BOM = version manager for 300+ Spring libs. mvn package = creates fat .jar with all deps inside. Maven Central = npmjs.org for Java.
Spring Framework

Spring Core — IoC & Dependency Injection

IoC is the foundational pattern Spring is built on. Everything else (Boot, MVC, Security, Data) plugs into this container.

🧠 The Mental Model

Normally YOU create objects: UserService service = new UserService(repo);. With IoC, you flip it — you say "I need a UserService" and Spring creates it and gives it to you. Spring is the factory manager. Your code declares needs (dependencies), Spring figures out how to satisfy them. That's Inversion of Control.

The Problem IoC Solves

Without IoC (tightly coupled) 
// You manually wire everything
public class OrderController {
  private OrderService orderService;

  public OrderController() {
    // Hard-coded dependency creation
    UserRepository userRepo =
      new UserRepository(
        new DatabaseConnection(
          new Config("db.properties")
        )
      );
    this.orderService =
      new OrderService(userRepo);
  }
}
// Problems:
// - Hard to test (can't mock)
// - Change DB config → change 5 classes
// - Duplicated creation logic everywhere
With Spring IoC (loosely coupled) 
// Spring creates & wires everything
@RestController
public class OrderController {

  // "I need an OrderService"
  // Spring provides one
  @Autowired  // or constructor injection
  private OrderService orderService;

  // That's it. Spring handles:
  // - Creating OrderService
  // - Creating its dependencies
  // - Managing lifecycle
  // - Singleton scope by default
}
// Benefits:
// - Easy to test (inject mocks)
// - Change DB → change 1 config file

Spring Beans — What Goes in the Container

A "Bean" is just a Spring-managed object
// 4 ways to declare a Bean:

// 1. @Component — generic bean (+ @Service, @Repository, @Controller)
@Service  // tells Spring: manage this class
public class EmailService { ... }

// 2. @Bean in a @Configuration class
@Configuration
public class AppConfig {
  @Bean
  public RestTemplate restTemplate() {
    return new RestTemplate(); // Spring manages lifecycle
  }
}

// 3. Spring Boot auto-configuration (see next section)
// 4. @ComponentScan — Spring scans packages for @Component classes

// Bean scopes:
@Scope("singleton") // default — one instance for whole app
@Scope("prototype") // new instance each time requested
@Scope("request")   // new instance per HTTP request
@Scope("session")   // new instance per HTTP session

Constructor Injection vs Field Injection

Field Injection (avoid) 
@Service
public class OrderService {

  @Autowired  // ← avoid this
  private OrderRepository repo;

  // Problems:
  // - Can't test without Spring context
  // - Hidden dependencies
  // - Can't make fields final
  // - Circular dep problems hidden
}
Constructor Injection (preferred) 
@Service
public class OrderService {

  private final OrderRepository repo;

  // @Autowired optional if single constructor
  public OrderService(OrderRepository repo) {
    this.repo = repo;
  }
  // Benefits:
  // - Testable without Spring
  // - Immutable (final field)
  // - Circular deps fail at startup
  // - Lombok @RequiredArgsConstructor
}
⚡ Recall Trigger
IoC = Spring creates + wires objects, not you. Bean = Spring-managed object. @Component/@Service/@Repository = tell Spring to manage this class. @Autowired = "give me a bean of this type". Singleton scope = default, one instance shared. Constructor injection = preferred (testable, immutable, clear deps).
Spring Boot

Spring Boot — Auto-Configuration Magic

Spring Boot is Spring with all the config pre-done. It's the difference between assembling a car from parts vs buying one ready to drive.

🧠 What Spring Boot Actually Does

Spring Framework (pre-Boot) required hundreds of lines of XML config to set up a web server. Spring Boot reads your classpath, sees you have spring-boot-starter-web, and auto-configures Tomcat, Jackson, MVC, error handling — all of it. The magic word is Auto-Configuration. "If you have X on classpath and Y bean doesn't exist → create Y automatically."

Controllers — Your Route Handlers

@RestController — like Express router
@RestController              // = @Controller + @ResponseBody
@RequestMapping("/api/orders") // base path for all methods
public class OrderController {

  private final OrderService orderService;

  public OrderController(OrderService orderService) {
    this.orderService = orderService;
  }

  // GET /api/orders
  @GetMapping
  public List<Order> getAllOrders() {
    return orderService.findAll();
  }

  // GET /api/orders/42
  @GetMapping("/{id}")
  public ResponseEntity<Order> getOrder(@PathVariable Long id) {
    return orderService.findById(id)
      .map(ResponseEntity::ok)
      .orElse(ResponseEntity.notFound().build());
  }

  // POST /api/orders
  @PostMapping
  @ResponseStatus(HttpStatus.CREATED)
  public Order createOrder(@RequestBody @Valid CreateOrderRequest req) {
    return orderService.create(req);
    // @Valid triggers Bean Validation (JSR-380)
  }

  // GET /api/orders?status=PENDING&page=0&size=20
  @GetMapping("/search")
  public Page<Order> search(
    @RequestParam String status,
    Pageable pageable        // Spring auto-injects from query params
  ) {
    return orderService.findByStatus(status, pageable);
  }
}

Exception Handling — Global Error Handler

@ControllerAdvice — Centralized Error Handling
@RestControllerAdvice  // handles exceptions from ALL controllers
public class GlobalExceptionHandler {

  @ExceptionHandler(ResourceNotFoundException.class)
  @ResponseStatus(HttpStatus.NOT_FOUND)
  public ErrorResponse handleNotFound(ResourceNotFoundException ex) {
    return new ErrorResponse("NOT_FOUND", ex.getMessage());
  }

  @ExceptionHandler(MethodArgumentNotValidException.class)
  @ResponseStatus(HttpStatus.BAD_REQUEST)
  public ErrorResponse handleValidation(MethodArgumentNotValidException ex) {
    List<String> errors = ex.getBindingResult().getFieldErrors()
      .stream()
      .map(fe -> fe.getField() + ": " + fe.getDefaultMessage())
      .collect(Collectors.toList());
    return new ErrorResponse("VALIDATION_FAILED", errors);
  }
}

// Request Validation DTOs
public record CreateOrderRequest(
  @NotBlank String customerId,
  @NotEmpty List<OrderItem> items,
  @Positive BigDecimal totalAmount
) {}
⚡ Recall Trigger
DispatcherServlet = front controller, receives all requests. @RestController = @Controller + auto JSON serialization. @GetMapping/@PostMapping = route handlers. @PathVariable = /orders/{id}. @RequestBody = parse JSON body. @RequestParam = ?key=value. @ControllerAdvice = global exception handler. @Valid = trigger Bean Validation annotations.
Database Layer

Spring Data JPA — Your ORM

Spring Data JPA wraps Hibernate ORM. You define entities and repository interfaces — Spring generates all the SQL for you.

Entity → Repository → Service → Controller (The Layered Pattern)
// 1. Entity — maps to DB table
@Entity
@Table(name = "orders")
public class Order {

  @Id
  @GeneratedValue(strategy = GenerationType.IDENTITY)
  private Long id;

  @Column(nullable = false)
  private String customerId;

  @Enumerated(EnumType.STRING)
  private OrderStatus status;

  @CreationTimestamp
  private LocalDateTime createdAt;

  // One Order has many OrderItems
  @OneToMany(mappedBy = "order", cascade = CascadeType.ALL)
  private List<OrderItem> items = new ArrayList<>();
}

// 2. Repository — Spring generates queries from method names
public interface OrderRepository
    extends JpaRepository<Order, Long> {

  // Spring reads method name → generates SQL
  List<Order> findByStatus(OrderStatus status);
  List<Order> findByCustomerIdAndStatusOrderByCreatedAtDesc(
    String customerId, OrderStatus status);

  // Custom JPQL query
  @Query("SELECT o FROM Order o WHERE o.createdAt > :since")
  List<Order> findRecentOrders(@Param("since") LocalDateTime since);

  // JpaRepository already gives you:
  // save(), findById(), findAll(), deleteById()
  // findAll(Pageable), count(), existsById()
}

N+1 Query Problem — The Most Common Spring Data Bug

⚠️ N+1: The Silent Performance Killer
// THE PROBLEM: Fetching 100 orders + their items
List<Order> orders = orderRepo.findAll();
for (Order order : orders) {
  order.getItems().size(); // ← TRIGGERS 100 EXTRA QUERIES!
}
// Total: 1 query (orders) + 100 queries (items) = 101 queries
// Hibernate default: LAZY loading = query per access

// THE FIX 1: @EntityGraph (fetch join)
@EntityGraph(attributePaths = {"items"})
List<Order> findAll(); // ← ONE query with JOIN

// THE FIX 2: JPQL JOIN FETCH
@Query("SELECT DISTINCT o FROM Order o JOIN FETCH o.items")
List<Order> findAllWithItems();

// THE FIX 3: Use spring.jpa.show-sql=true in dev
// See exactly how many queries Hibernate fires
// Use Hypersistence Optimizer or p6spy for deeper analysis

Transactions — @Transactional

@Transactional — All or Nothing
@Service
public class OrderService {

  @Transactional  // if ANY exception → rollback ALL DB changes
  public Order createOrder(CreateOrderRequest req) {
    Order order = buildOrder(req);
    orderRepo.save(order);          // DB write 1
    inventoryService.deduct(req); // DB write 2
    paymentService.charge(req);   // DB write 3
    // If paymentService throws → writes 1&2 ROLLED BACK
    return order;
  }

  // Read-only optimization
  @Transactional(readOnly = true)
  public List<Order> findAll() {
    return orderRepo.findAll();
    // readOnly=true: DB can optimize (skip dirty checking)
  }
}

// ⚠️ @Transactional only works when called from OUTSIDE the class
// Self-invocation (calling @Transactional method from same class)
// bypasses the proxy → no transaction! Common gotcha.
⚡ Recall Trigger
@Entity = maps class to DB table. JpaRepository = auto-generated CRUD + custom queries. Method name queries = Spring reads method name and writes SQL. LAZY loading = default, queries on access → causes N+1. @EntityGraph/JOIN FETCH = fix N+1. @Transactional = all-or-nothing DB operations, only works via proxy (external calls).
Security

Spring Security — Auth & AuthZ

Spring Security intercepts every request before it reaches your controller. JWT + OAuth2 are the modern patterns.

Security Filter Chain — The Request Gauntlet

CorsFilter
Check CORS headers. Block cross-origin requests.
Layer 1
JwtAuthenticationFilter
Extract JWT from header → validate → set SecurityContext.
Layer 2
AuthorizationFilter
Check @PreAuthorize / hasRole against SecurityContext.
Layer 3
DispatcherServlet → Controller
Request reaches your code only if it passed all above.
Your Code
SecurityFilterChain — Spring Boot 3 Config
@Configuration
@EnableWebSecurity
@EnableMethodSecurity  // enables @PreAuthorize on methods
public class SecurityConfig {

  @Bean
  public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
    return http
      .csrf(csrf -> csrf.disable())    // REST APIs use JWT, not sessions
      .sessionManagement(s -> s
        .sessionCreationPolicy(STATELESS)) // no session cookies
      .authorizeHttpRequests(auth -> auth
        .requestMatchers("/api/auth/**").permitAll()  // public
        .requestMatchers("/api/admin/**").hasRole("ADMIN")
        .anyRequest().authenticated()     // all else → JWT required
      )
      .addFilterBefore(jwtFilter, UsernamePasswordAuthenticationFilter.class)
      .build();
  }

  // Method-level security
  @PreAuthorize("hasRole('ADMIN') or #userId == authentication.name")
  public User getUser(String userId) { ... }
}
⚡ Recall Trigger
Filter Chain = security gauntlet before controller. JWT = stateless auth token, no session. SecurityContext = holds current user per-thread. @PreAuthorize = method-level role check. STATELESS sessions = no cookies, each request carries JWT. csrf.disable() = correct for REST APIs (CSRF is a browser-session attack).

Feign Client — HTTP Between Services

OpenFeign — Like axios but declarative, no implementation needed
// Define the interface — Spring generates implementation
@FeignClient(name = "inventory-service")  // service name in Eureka
public interface InventoryClient {

  @GetMapping("/api/inventory/{productId}")
  InventoryResponse checkStock(@PathVariable String productId);

  @PostMapping("/api/inventory/deduct")
  void deductStock(@RequestBody DeductRequest request);
}

// Use it like a regular service (Spring creates HTTP client):
@Service
public class OrderService {
  private final InventoryClient inventoryClient;

  public Order createOrder(CreateOrderRequest req) {
    // This makes an HTTP call to inventory-service
    // Eureka resolves "inventory-service" to real IP:port
    InventoryResponse stock = inventoryClient.checkStock(req.getProductId());
    if (!stock.isAvailable()) throw new OutOfStockException();
    // ...
  }
}

Circuit Breaker Pattern — Resilience4j

Circuit Breaker — Don't Let One Slow Service Kill Your App
// Without circuit breaker: inventory-service slow → 30s thread lock
// → all order threads waiting → order-service dies too
// The "cascading failure" problem

@CircuitBreaker(name = "inventory", fallbackMethod = "fallbackStock")
@Retry(name = "inventory")
@TimeLimiter(name = "inventory")  // timeout after 2s
public InventoryResponse checkStock(String productId) {
  return inventoryClient.checkStock(productId);
}

// Fallback: what to do when circuit OPEN
public InventoryResponse fallbackStock(String productId, Exception ex) {
  log.warn("Inventory unavailable, using default");
  return InventoryResponse.builder().available(true).build();
  // Or: throw custom exception, or return cached value
}

// Circuit states:
// CLOSED  → normal, requests flow through
// OPEN    → failing fast, fallback used (after X% failures)
// HALF-OPEN → test if service recovered (let some calls through)
⚡ Recall Trigger
Eureka = phone book for services (register + discover). Config Server = one Git repo for all service configs. API Gateway = single entry, routes to services. Feign = write an interface, get HTTP client. Circuit Breaker = fail fast when downstream slow → fallback → prevent cascading. Distributed Tracing = one trace ID follows request through all services.
Containerization

Docker — Packaging Your App

Docker solves "works on my machine." Your Spring Boot jar + its exact environment = one portable image. Runs identically on dev laptop, CI server, and AWS.

🧠 The Core Mental Model

A Docker image is like a recipe (read-only). A container is the running dish made from that recipe. You can make 100 dishes from the same recipe. The image includes your app AND its entire operating system layers — no "I need Java 21 installed on the server" problem. Everything is baked into the image.

Dockerfile for Spring Boot

Multi-Stage Build — Slim Production Image
# Stage 1: Build (uses full JDK, discarded after)
FROM eclipse-temurin:21-jdk-alpine AS builder
WORKDIR /app
COPY pom.xml .
COPY src ./src

# Download deps (cached layer — only re-runs if pom.xml changes)
RUN mvn dependency:go-offline -B

# Build the fat jar
RUN mvn package -DskipTests

# Stage 2: Runtime (uses slim JRE, ~200MB vs ~600MB)
FROM eclipse-temurin:21-jre-alpine
WORKDIR /app

# Extract layered jar (faster restarts, better caching)
COPY --from=builder /app/target/*.jar app.jar

# Spring Boot 3 layertools
RUN java -Djarmode=layertools -jar app.jar extract

# Run the app
ENTRYPOINT ["java", "-jar", "app.jar"]
EXPOSE 8080

📦
Image vs Container

Image = cookie cutter (recipe, read-only). Container = actual cookie made from cutter (running instance). 1 image → unlimited containers. Kill a container → nothing lost, make a new one from same image.

🏗️
Layer Caching Hook

Dockerfile layers = pancake stack. Each instruction = one layer. If layer N changes, all layers below rebuild. Put rarely-changing things first (base OS, dependencies) and frequently-changing things last (your app code). mvn dependency:go-offline before COPY src = deps cached until pom.xml changes.

🌐
Networking Hook

Containers in docker-compose share a virtual network. "postgres:5432" works inside compose because the service name IS the hostname. Outside compose = localhost:5432. That's why DB_URL changes between dev and compose.

🔄 What Breaks Without Understanding Docker
  • Copying WHOLE project before mvn dependency:resolve → deps re-download on every code change → 5 min builds.
  • Running as root in container → security risk, many registries reject it. Use USER 1001.
  • Not setting -Xmx JVM flag → JVM detects container memory wrong in old Java → OOMKilled unexpectedly.
  • Using latest tag in prod → unpredictable image pulls → different behavior after registry push. Always pin versions.
  • No .dockerignore → COPY . . sends target/ (500MB of compiled classes) into image build context → slow builds.
⚡ Recall Trigger
Image = recipe (read-only). Container = running instance. Multi-stage build = build with JDK, run with slim JRE. Layer caching = copy pom.xml before src, deps cached until pom changes. docker-compose = orchestrate local app + DB + Redis. .dockerignore = exclude target/, node_modules from build context.
Orchestration

Kubernetes — Running Containers in Production

Docker runs ONE container on ONE machine. Kubernetes runs MANY containers across MANY machines with auto-healing, scaling, rolling deploys, and service discovery.

🧠 The Mental Model

Docker Compose is a local dinner party you organize yourself. Kubernetes is a restaurant chain — you say "I want 5 replicas of my service, always healthy, restart if one dies, rollout new versions without downtime." K8s is the restaurant operations manager. You declare desired state. K8s continuously makes reality match your declaration.

Self-Healing Hook

K8s = hospital with automatic ICU. Pod (patient) dies → K8s immediately starts new one (replacement) to maintain "3 replicas desired." Liveness probe = "are you alive?" Readiness probe = "are you ready for patients?" Only ready pods get traffic.

🔄
Rolling Deploy Hook

Rolling deploy = replacing bus wheels while moving. K8s starts new pod → waits for ready → kills one old pod → repeats. At no point = zero pods. Zero downtime deploys by default. Rollback = undo last commit (kubernetes keeps history).

📋
Desired State Hook

K8s = thermostat. You set "temperature: 3 replicas." K8s checks every few seconds — if reality ≠ desired, it fixes it. Pod crashes = below desired → K8s starts new one. Node dies = pods move to other nodes. You declare WHAT, K8s figures out HOW.

⚡ Recall Trigger

ConfigMap = non-secret config. Secret = encrypted config (passwords, keys). Liveness probe → /actuator/health/liveness. Readiness probe → /actuator/health/readiness.

GitHub Actions — Spring Boot CI/CD Pipeline
# .github/workflows/ci-cd.yml
name: CI/CD Pipeline

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest
    services:
      postgres:
        image: postgres:16
        env: {POSTGRES_PASSWORD: testpass}
        options: --health-cmd pg_isready
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with: {java-version: '21', distribution: 'temurin'}
      - name: Cache Maven deps
        uses: actions/cache@v3
        with:
          path: ~/.m2
          key: ${{ runner.os }}-m2-${{ hashFiles('**/pom.xml') }}
      - name: Run Tests
        run: mvn test -B
        env:
          SPRING_DATASOURCE_URL: jdbc:postgresql://localhost:5432/testdb

  build-and-push:
    needs: test
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Build Docker image
        run: docker build -t ${{ vars.ECR_REGISTRY }}/myapp:${{ github.sha }} .
      - name: Push to ECR
        run: |
          aws ecr get-login-password | docker login --username AWS ...
          docker push ${{ vars.ECR_REGISTRY }}/myapp:${{ github.sha }}
      - name: Deploy to ECS
        run: aws ecs update-service --cluster prod --service myapp --force-new-deployment

pip, venv & Poetry — Python's Package Management

Python's package ecosystem mirrors Java's Maven but with some important differences around virtual environments and dependency hell.

🧠 The Critical Difference From Java

Java's Maven installs packages globally in ~/.m2 and they don't conflict between projects (different groupId paths). Python installs globally by default — Project A needs Django 3.2 and Project B needs Django 4.2? They clash. That's why virtual environments are non-negotiable in Python. Every project gets its own isolated Python installation.

⚡ Recall Trigger
@shared_task = Spring @Async. .delay() = submit task to queue (non-blocking). Redis/RabbitMQ = broker (holds task queue). Worker process = separate process that pulls and runs tasks. Beat = cron scheduler (periodic tasks). Retry with countdown = Spring Retry equivalent.

📖 The Big 30-Second Recap

JVM = runs Java bytecode (like V8 runs JS). Maven = npm + build tool (pom.xml). Spring IoC = container creates + wires beans. Spring Boot = auto-config + starters + embedded Tomcat. Spring MVC = @RestController handles HTTP. Spring Data JPA = Hibernate ORM with repo pattern. Spring Security = filter chain guards endpoints. Spring Cloud = Eureka + Config + Gateway + Feign + CircuitBreaker for microservices. Docker = image (recipe) + container (instance). Kubernetes = desired state orchestration at scale. AWS = ECS/EKS (run containers) + RDS (DB) + SQS (queue) + S3 (files). Django = batteries-included Python framework (ORM + admin + auth). DRF = Spring MVC for Python (Serializers + ViewSets). Celery = async task queue (like @Async + RabbitMQ).
